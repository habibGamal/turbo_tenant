<task>
Laravel 12 + Filament 4 + Inertia/React multi-tenant restaurant store (stancl/tenancy). Replace the per-tenant
`theme.css` file with store-owner-editable theme colors stored as a normal store setting, edited in a new
"Appearance" tab of the existing Store Settings admin page.

CURRENT STATE (verify by reading the files):
- `app/Services/TenantService.php` has `createThemeFile()` which writes a fixed `storage/tenant{id}/app/theme.css`
  (shadcn CSS variables) and is called from the tenant setup method in the same file.
- `routes/tenant.php` has a `Route::get('/theme.css', ...)` serving that file.
- `resources/views/app.blade.php` inlines it: `@if($isTenant && Storage::exists('theme.css')) <style id="tenant-theme">...`.
  The top of that blade already resolves `$settingService` (SettingService) when a tenant is active.
- BUG: `resources/css/app.css` has an `@theme { --color-primary: hsl(0 0% 9%); ... }` block with HARD-CODED colors,
  so Tailwind utilities like `bg-primary` compile to `var(--color-primary)` = a fixed value and NEVER read the
  `--primary` etc. variables defined in `:root`. Overriding `--primary` therefore has no effect on utilities.
  Also `tailwind.config.js` (loaded via `@config`) defines colors as `hsl(var(--primary))` while the `:root`
  values are `oklch(...)` — invalid. The `:root` block has no `--destructive-foreground`.
- Settings live in the StoreSettings plugin: `app/Plugins/StoreSettings/`. Keys are cases of `app/Enums/SettingKey.php`
  (with `defaultValue()` and `type()`; JSON settings use `SettingType::Json`). Tabs are `SettingsSection`
  implementations in `app/Plugins/StoreSettings/src/Settings/` (see `StoreCardsSettingsSection.php` as the model),
  registered + tagged `store-settings.sections` in `StoreSettingsServiceProvider.php`. The page
  `src/Filament/Pages/Settings.php` loads/saves every key listed by each section's `keys()`.
- The storefront is light-mode only in practice (no `.dark` toggle on the storefront).

WHAT TO BUILD:
1. New `SettingKey::THEME = 'theme'`, type Json, default `[]`. Value shape:
   `{"preset": string, "primary": "#rrggbb", "secondary": "#rrggbb", "radius": "none|sm|md|lg|xl"}`.
2. A small theme service in the StoreSettings plugin (e.g. `src/Theme/ThemePresets.php` + `src/Theme/ThemeCssBuilder.php`):
   - ~6 named presets (Arabic labels), each with primary + secondary hex + radius. Include a neutral "default"
     matching today's look (primary ≈ #171717) and a terracotta preset with primary #893c25 (the brand color used
     elsewhere as the PWA theme_color).
   - `build(array $theme): string` returns a CSS string `:root{...}` setting: `--primary`, `--primary-foreground`,
     `--ring` (= primary), `--secondary`, `--secondary-foreground`, `--accent`, `--accent-foreground`, `--radius`.
     Foreground colors are chosen automatically (white or near-black) by WCAG contrast against the background color.
     Radius map: none=0rem, sm=0.375rem, md=0.5rem, lg=0.75rem, xl=1rem.
   - SECURITY: only accept colors matching `/^#[0-9a-fA-F]{6}$/` and radius from the fixed map. Anything else is
     dropped (falls back to the CSS defaults). Never interpolate raw user strings into the CSS. Empty/invalid
     input returns an empty string.
3. New `StoreAppearanceSettingsSection` (tab label 'المظهر والألوان', heroicon-o-swatch, sort between the existing
   sections — read their sort values) with: a preset `Select` that, when changed, fills the color pickers and radius
   (`->live()` + `afterStateUpdated`); `ColorPicker` for primary and secondary with hex regex validation; a radius
   `Select`. Use nested state paths under the `theme` key (e.g. `theme.primary`) so the whole value saves as one JSON
   setting through the existing Settings page save loop. `keys()` returns `[SettingKey::THEME]`. Register and tag it
   in `StoreSettingsServiceProvider` like the others. Admin UI text is Arabic, like the other tabs.
4. `resources/views/app.blade.php`: replace the `Storage::exists('theme.css')` block with
   `<style id="tenant-theme">` containing the builder output for the tenant's `theme` setting (only when non-empty).
   Keep it AFTER the main stylesheet so it wins. Keep the `</style` escaping.
5. Fix the CSS plumbing so variables actually drive utilities:
   - In `resources/css/app.css` replace the hard-coded color `@theme` block with `@theme inline { --color-primary: var(--primary); ... }`
     for every color currently in that block (background, foreground, card(+fg), popover(+fg), primary(+fg),
     secondary(+fg), muted(+fg), accent(+fg), destructive(+fg), border, input, ring, chart-1..5), and
     `--radius-lg: var(--radius); --radius-md: calc(var(--radius) - 2px); --radius-sm: calc(var(--radius) - 4px);`.
   - Add `--destructive-foreground` to `:root` and `.dark`.
   - Remove the `colors` (and border-radius, if it duplicates) entries from `tailwind.config.js` so they don't
     conflict; leave the rest of that config alone.
   - The default (no theme setting) storefront must look the same as before (neutral palette).
6. Remove the file mechanism: delete `createThemeFile()` and its call in `TenantService`, and the `/theme.css` route.
   Do NOT delete existing theme.css files on disk under storage/. Grep for any other references
   (tests, e2e under tests/, docs like THEME_GUIDE.md) and update code/tests that reference them.
7. Pest tests (look at tests/Feature/Filament/SettingsUxTest.php and tests/Feature/Filament/StoreSettingsCanonicalKeysTest.php
   for setup conventions, and update them if they enumerate sections/keys):

     CSS injection attempts like `#fff;}</style><script>` and unknown radius are dropped; empty input → ''.
   - the appearance section is registered and saving the settings page persists the `theme` JSON.
   - the storefront HTML contains `id="tenant-theme"` with the primary color when the setting is set.
